# 🥋 Ponytail Governance Directive for DAGR

> **Status:** ACTIVE & ENFORCED ACROSS ENTIRE CODEBASE  
> **Level:** `full` (Default)  
> **Philosophy:** The best code is the code never written. Reach for stdlib and native OS features before adding crates or boilerplate.

---

## 🪜 The Ponytail Ladder for DAGR (Enforced on Every Commit)

1. **Does this need to exist at all?** (YAGNI) — Skip speculative abstractions. No trait for 1 struct, no factory for 1 type.
2. **Already in the codebase?** — Reuse existing utilities before creating new files.
3. **Stdlib does it?** — Use Rust `std::fs`, `std::collections::HashSet`, `std::path::Path` before pulling crates.
4. **Native platform feature covers it?** — Use `clonefile(2)` on macOS and `reflink` on Linux for CoW before building complex userspace file trackers.
5. **Already-installed crate solves it?** — Use existing workspace dependencies. Never add a new crate if 5 lines of Rust do the job.
6. **Can it be one line / one clean function?** — Keep it minimal.
7. **Only then:** Write the minimum code that actually works.

---

## 🏷️ Deliberate Simplification Ledger (`ponytail:` tags)

---

## 🚫 Hard YAGNI Prohibitions in DAGR:
- ❌ No microservices or Docker containers in Phase 1.
- ❌ No abstract generic factories where concrete functions work.
- ❌ No hand-rolled tokenizers when `tiktoken-rs` or simple word bounds suffice.
- ❌ No boilerplate scaffolding "for future phases" — implement when that phase arrives.
